# 실제 로그에 적용하기 — 가장 먼저 확인할 것

이 저장소의 숫자는 합성 데이터에서 나왔습니다. 실제 점검 로그에 적용할 때는 **효과를 추정하기 전에, 이 로그로 효과를 추정해도 되는지부터** 확인합니다. 실제 로그의 예는 유비스 마스터의 점검·고장수리·A/S 이력입니다. 확인 순서는 아래와 같습니다.

## 1. 로그를 (설비 × 주) 표로 만듭니다

| 이 저장소의 열 | 실제 로그에서 만드는 법 (예시) |
|---|---|
| `asset`, `week`, `site` | 설비 ID, 결정 시점(주 단위로 내림), 고객사·건물 |
| `treated` | 그 주에 해당 설비의 점검 기록(NFC/비콘 체크)이 한 건이라도 있는가 |
| `y` | 그 주부터 4주 안에 **비계획** 고장 접수(작업지시 유형이 고장수리)가 있었는가. 점검에서 발견해 예방정비로 처리한 건은 고장이 아닙니다 |
| `grade_last`, `wsv` | 직전 점검의 종합 판정(양호/주의/불량 → 0/1/2), 마지막 점검 후 경과 주 |
| `bd` | 최근 고장 건수를, 오래된 건일수록 비중을 줄여 더한 값(지수 감쇠 합, 예: 반감기 10주) |
| `cmp` | 최근 민원·A/S 접수를 같은 방식(지수 감쇠 합)으로 더한 값. **점검 결정에 가장 강하게 영향을 주는 변수일 가능성이 높습니다.** 빠뜨리면 점검 여부와 고장에 동시에 영향을 주는 요인(교란)이 남습니다 |
| `open_wo` | 아직 닫히지 않은 수리 접수(작업지시)가 있는가 |
| `due` | 법정 점검 기한이라 달력으로 점검이 정해진 행 (분석에서 빠집니다) |
| `y_prev` | (선택, 권장) 점검 이전 4주의 고장. 음성 대조(점검 이전 고장에도 '효과'가 나오는지 보는 검사)에 씁니다 |

열 이름이 다르면 `LogSpec` 으로 연결해 줍니다.

```python
from averted.audit import run_audit
from averted.causal.data import LogSpec
spec = LogSpec(unit="설비ID", time="주", treatment="점검", outcome="고장", site="건물",
               numeric=("연식", "중요도", "직전판정", "경과주", "최근고장", "민원", "수리접수"),
               categorical=("종류",), category_levels={"종류": ["펌프", "냉동기", "공조기"]},
               due="법정기한", prior_outcome="직전4주고장")
report = run_audit(df, spec=spec)
```

## 2. 감사 결과를 읽는 순서

`run_audit` 이 돌려주는 `report` 를 아래 순서로 읽습니다. 감사는 로그를 검사해 신호등 색으로 판정하는 단계입니다.

1. **`data.rows_excluded_due`**: 법정 점검 행이 얼마나 빠졌는지 봅니다. 점검 대부분이 달력으로 정해져 있다면 점검 여부가 달라지는 경우가 거의 없습니다. 그러면 **효과를 추정할 수 없습니다.** 이때 감사는 "겹침" 경고를 냅니다(아래 2번). 답은 무작위 파일럿입니다.
2. **`overlap`**: 비교할 상대가 있는지 봅니다. 점검 확률이 극단(거의 0 이거나 1)인 행의 비율과 유효 표본을 확인합니다. 유효 표본은 가중치를 반영해 계산한 실질 표본 수입니다. 위험한 설비만 점검하는 사이트라면 점검하지 않은 비교 대상(대조군)이 비어 있습니다.
3. **`balance`**: 점검한 설비와 안 한 설비를 가중해 맞춘 뒤에도 SMD 가 큰 변수가 남아 있는지 봅니다. SMD(표준화 평균 차이)는 두 집단의 평균이 얼마나 다른지를 나타냅니다.
4. **`negative_control`**: 음성 대조입니다. 점검 이전의 고장에 "효과"가 나오면 숨은 교란, 곧 기록에 없는 이유로 점검 대상을 골랐다는 신호입니다. 다만 **그 이유가 약하면 잡아내지 못합니다** (`docs/failures.md`).
5. **`benchmarks`·`tipping`**: 기록된 변수 하나를 뺐을 때 추정이 얼마나 움직이는지 보여 줍니다. 이 이동량이 추정된 효과보다 크면, 기록에 없는 요인 하나만으로도 결론이 뒤집힐 수 있습니다.
6. **`estimates`**: 순진한 비교(점검한 설비와 안 한 설비를 그대로 비교)와 AIPW 를 견줍니다. AIPW 는 점검 여부와 고장을 각각 모형으로 맞춰 효과를 보정하는 추정 방법입니다. 둘의 차이가 클수록 로그에 섞인 교란이 큽니다. AIPW 구간이 0 을 포함하면 말할 수 있는 것이 없습니다.
7. **`pilot`**: 위 숫자로 계산한 파일럿 규모입니다.

## 3. 무작위 파일럿 절차 (실증 프로젝트에 넣을 것)

무작위 파일럿은 점검할 설비를 사람이 고르지 않고 동전 던지기로 정해서, 점검의 효과를 직접 비교하는 시험입니다.

1. 고객사 한 곳에서 **법정 점검 대상이 아닌** 설비 가운데 일부(예: 30%)를 무작위로 골라 파일럿 설비로 지정합니다.
2. 파일럿 설비는 매주 **동전 던지기**로 점검 대상을 정합니다. 확률은 평소 점검 비율과 비슷하게 잡습니다. 현장 담당자가 직접 고르지 않습니다.
3. 결과는 점검 이후 4주 안에 생긴 비계획 고장입니다. 4주마다 한 시점만 셉니다. 관찰 기간(창)이 서로 겹치지 않게 하려는 것입니다.
4. 규모는 `POST /v1/pilot/plan` 또는 콘솔의 계획기로 정합니다. **전체 설비를 대상으로 하면 효과가 작아서 규모가 매우 커집니다.** 합성 세계에서 계산하면 한 고객사 규모의 수 배 이상입니다. 민원이 접수된 설비처럼 효과가 큰 층만 대상으로 하면 규모가 크게 줄어듭니다.
5. 분석은 점검한 설비와 안 한 설비의 평균 차이를 구하는 것입니다. 구간은 설비 단위로 다시 뽑아 보는 방식(군집 부트스트랩)으로 붙입니다. 무작위로 정했으므로 보정은 필요 없습니다. 관측 로그의 AIPW 추정이 이 구간 밖에 있으면, 관측 추정을 의사결정에 쓰지 않습니다.

## 4. 이 저장소가 실제 로그에서 알려 주지 못하는 것

- 기록에 없는 교란이 없다는 것은 확인해 주지 못합니다. 그것은 가정입니다. 감사는 가정이 깨졌다는 **증거를** 찾을 뿐, 깨지지 않았다는 것을 **증명하지는** 못합니다.
- 점검의 질 차이(깊이, 점검자 숙련도)는 알 수 없습니다. 여기서는 "점검"을 한 가지 행위로 봅니다.
- 점검 **프로그램**(주기 변경)의 효과는 알 수 없습니다. 추정하는 것은 "이번 주에 한 번 더 점검"했을 때의 효과입니다.
