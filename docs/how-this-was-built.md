# 이 저장소가 만들어진 방식

사람이 방향·수용 기준·"무엇을 주장하지 않을지"를 정하고, 코딩 에이전트(Claude)가 조사·구현·측정을 실행했다. 커밋 트레일러에 그대로 적혀 있다.

## 주제를 고른 과정

1. 앞서 만든 저장소(harbinger, 센서 없는 설비의 고장 예측)는 "예지보전이라 흔하고 복잡해 보인다"는 평가를 받았다.
2. 조사: 회사(디더블유아이) 최신 기사, 채용·합격 후기(찾지 못함), 국내 유사 프로젝트의 포화도(예지보전·전력 예측·안전모 탐지·RAG 챗봇은 포화), 면접관이 포트폴리오에서 보는 것(문제 정의·평가 설계·실패 공개), 후보 주제의 선행 연구.
3. 회사가 내세우는 문구는 "장애를 예측하고 **최적의 운영 시나리오를 제시**"다. 예측 다음 단계(어디에 손을 쓰면 효과가 있나)가 빠져 있었고, 국내 공개 저장소에서 점검의 인과효과·점검 배분을 다룬 것은 찾지 못했다. (선행 연구는 해외에 있다 — `docs/prior-work.md`.)

## 사람이 판단한 것, 에이전트가 틀렸던 것

- **처음 시뮬레이터는 위험순과 효과순이 같았다.** 효과가 위험에 단조로우면 질문 자체가 사라진다. 현장에서 둘이 갈라지는 이유(수리 접수된 설비, 순찰로 못 찾는 설비, 교체 대상)를 메커니즘으로 넣었고, 그 사실을 `docs/simulator.md` 에 "발견이 아니라 가정"이라고 적었다.
- **처음에는 학습한 효과 모형이 위험순을 못 이겼다.** 사이트 8~24곳 규모의 초기 실험에서 트리 DR-learner·T-learner·DragonNet 모두 그랬다. 구조 없는 효과 학습은 이 데이터량으로는 어렵다는 것이 결론이고, 구조를 준 모형(반응도)이 고객사를 풀링해야 이긴다는 것을 학습곡선으로 보였다. 모형을 시뮬레이터에 맞춰 튜닝하는 대신 단순 규칙(수리 접수 제외)을 기준선에 넣었고, 작은 데이터에서는 그 규칙이 학습 모형을 이긴다는 것도 그대로 적었다.
- **감사 판정이 정상 세계를 빨강으로 표시했다.** 민감도(숨은 교란에 대한 취약성)를 신호등에 섞었기 때문이다. 데이터로 확인되는 문제와 가정 의존도를 분리했다.
- **파일럿 검정력이 포화됐다.** 설비 내 상관 때문에 기간을 늘려도 검정력이 오르지 않는다 — 계산기가 그것을 "도달 불가"로 말하게 했다.
- **스레드 경쟁.** 병렬 워커의 트리 학습이 코어를 서로 빼앗아 실험이 5배 느려졌다. 워커당 스레드를 1개로 고정했다.

## AI 사용 공개

코드·문서의 초안은 에이전트가 썼다. 사람이 하지 않았다면 아무도 검토하지 않았을 부분을 테스트로 고정했다.
- 정답(포크)이 직접 시뮬레이션과 일치하는가 (`tests/test_world.py`)
- 추정기가 정답을 아는 자료에서 복원되는가, **econml 의 같은 추정기와 일치하는가** (`tests/test_estimators.py`)
- JS 포트(파일럿 계획기)가 파이썬과 일치하는가 (`tests/test_pilot_parity.py`)
- 문서의 숫자가 산출물과 일치하는가 (`scripts/fill_numbers.py --check`, CI)

## 재현

```bash
make install && make pipeline     # 시뮬레이션·평가·학습곡선·몬테카를로 (약 1~2시간)
make test
make serve                         # http://localhost:8000/console/
```
